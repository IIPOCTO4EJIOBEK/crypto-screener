# Архитектура ИИ-скринера

Документ описывает, как устроен ассистент: из чего он состоит, что уже
работает, что ещё нет и почему сделано именно так.

## Что ассистент делает

Находит на биржах монеты, где прямо сейчас складывается понятная ситуация
(формация), и по каждой даёт разбор: что произошло, откуда вход, где стоп,
куда целиться и при каком условии разбор отменяется. Отдельно следит за
стаканом — крупные лимитные заявки, их жизнь и признаки спуфинга. И ведёт
базу знаний по методике поиска.

Чего он **не** делает: не торгует сам, не отправляет заявки, не говорит
«покупай». Ключ от биржи ему не нужен — всё, что он читает, публично.

## Слои

```
               ▼
        src/analysis/formations.py     12 детекторов формаций

               │
               ▼
        src/backtest/walk.py           прогон по истории
               │

        src/rag/                             поиск по методике
        src/llm/                             разбор словами
```

## Принципы, из которых всё вытекает

**Считать кодом, а не моделью.** Все числа — NATR, объёмы, корреляции,
уровни, расстояния до стопа — считает Python. Языковая модель получает
готовый разбор и пересказывает его словами. Модель, считающая числа,
ошибается молча и правдоподобно; код ошибается громко и воспроизводимо.

**Формация — это разбор, а не сигнал.** У каждой находки есть вход, стоп,
цель, условие отмены и список причин, почему она найдена. «Купи» без
объяснения — это не результат работы скринера.

**Честные данные.** Чего биржа не отдаёт, того в ассистенте нет. Ни одна
цифра не додумывается: если данных нет — так и написано.

**Порог — из источника, а не из подгонки.** Где есть исследование с числом
(сжатие `ER ≤ 0.5–0.7`, пробой «2× среднего», дистанция спуферов 7.45 б.п.),
порог берётся оттуда. Где исследования нет — стоит пометка, что это оценка.

## Как устроен маршрут к биржам

Прокси из окружения режет часть биржевых доменов по таймауту, а Binance
через него, наоборот, отвечает быстрее и целиком. Поэтому в `market.py`
держатся две сессии — с прокси и без — и для каждой биржи заранее известно,
какой маршрут предпочтителен; при неудаче запрос автоматически повторяется
по второму. Гео-блок РФ накрывает только торговый домен Binance
(`api.binance.com`), публичные данные идут через `data-api.binance.vision`.

## Как устроен детектор формации

Общая схема одна для всех двенадцати:

1. Взять историю свечей, отбросить последнюю — она ещё формируется.
2. Пройти по последним `EVENT_WINDOW` закрытым свечам.
3. На каждой проверить условие формации (своё для каждого типа).
4. Если условие сошлось — собрать разбор: вход, стоп, цели, причины,
   условие отмены, уверенность.

Два решения, без которых схема не работает:

**Событие ищется в окне, а не на одной свече.** Пробой уровня — момент, а не
состояние. Детектор, срабатывающий ровно на свече пробоя, показывает пустой
экран почти всегда.

**Последняя свеча не участвует.** Её закрытие и объём меняются каждую
секунду; решение по ней — решение по незаконченным данным.

**Стоп не ставится внутри шума.** Если расстояние до стопа меньше половины
NATR, разбор выбрасывается: такой стоп собьёт первой же свечой, и формация
права не будет.

## Что показал прогон по истории

Прогон на шести монетах, трёх таймфреймах, 2708 сделках. Результат
разбирается отдельно в `docs/03-результаты-прогона.md`. Коротко: детекторы
находят реальную структуру, но у части формаций цель систематически ближе
стопа — то есть находка верная, а сделка по ней убыточная. Это разделяет
две разные задачи: «увидеть формацию» и «из неё заработать».

## Чего не хватает

**Хранилище.** PostgreSQL с pgvector под историю находок и под базу знаний.
Системный PostgreSQL на хосте недоступен без пароля sudo, поэтому план —
отдельный контейнер.

**Расписание.** Сейчас всё запускается руками. Нужен цикл: раз в N секунд
обойти список монет, прогнать детекторы, сложить находки в базу, отдать
изменившееся в уведомления.

**Список монет.** Откуда брать пары для обхода: по объёму, по волатильности,
по появлению в листингах. Сейчас список задаётся вручную.

**Новостной слой.** Анонсы бирж и события с метками времени, чтобы
сопоставлять их с движением цены (см. `docs/research/05-новостные-триггеры.md`).

**Профиль объёма.** VPVR, POC, value area — сила уровня по тому, сколько
объёма на нём проторговано. В исследовании помечено как подтверждённое,
в коде пока нет.

**Учёт издержек в прогоне.** Комиссии, фандинг и проскальзывание в
результатах не учтены. На младших таймфреймах они съедают заметную часть
движения, поэтому реальный результат хуже показанного.

## Границы достоверности

- У Digash опубликованы названия формаций и метрики, но не пороги
  детекторов. Все пороги в коде — либо из исследования, либо рабочая
  оценка; в коде они помечены.
- Окно поиска экстремума (40 свечей) задано для истории в 1000 свечей. На
  короткой истории оно сужается пропорционально, иначе уровней находится
  четыре штуки на монету.
- Прогон по истории не является проверкой доходности: он отвечает на
  вопрос «детектор вообще что-то находит и в какую сторону», а не
  «сколько на этом можно заработать».
