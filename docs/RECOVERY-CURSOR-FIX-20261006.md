# Исправление восстановления минут — 06.10.2026

В live-аудите 1000BONKUSDT курсор позиции был 1791307860000, старая WS-история заканчивалась 1791307560000, а REST уже содержал непрерывный диапазон 1791307860000–1791308160000. MinuteCache проверял непрерывность объединения целиком и ошибочно считал разрыв до курсора препятствием сопровождению. POLUSDT первоначально также ожидал историю, но восстановился автоматически до изменения кода.

MinuteCache теперь выбирает бары начиная с минуты курсора позиции и проверяет покрытие/непрерывность/цены требуемого интервала. Нужная незакрытая минута входа сохраняется округлением вниз. Разрывы внутри требуемого периода по-прежнему вызывают RecoveryPending; курсор при этом не продвигается. Запрос более раннего диапазона в том же кэше перепроверяется и не принимает прежнюю более короткую выборку.

22 теста recovery/fast-monitor прошли локально и на VPS. Код установлен с before-cursor резервом; monitor/recovery перезапущены, SQL и позиции не переписывались. Первичная проверка через 8 секунд ещё увидела waiting-recovery; повторный live-срез подтвердил errors=[], оба символа websocket+recovery, курсор 1000BONKUSDT продвинулся до 1791308220000. Monitor 2,046 сек, ok=true, busy_profiles=[]. Health и backup Result=success, failed units=0. Health-проверки не ослаблялись.

REST-резерв остаётся необходим при отсутствии свежих WS-свечей; восстановление может занимать несколько проходов, абсолютное отсутствие задержек не обещается. Лимиты 200 во всех семи профилях и страницы «из 200» повторно подтверждены.

Действия: docs/deploy_recovery_cursor_fix.py; локальный read-only аудит deployment/audit_recovery_gaps.py.
